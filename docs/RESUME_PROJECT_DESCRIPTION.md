# Resume Project Description

以下内容用于简历或项目介绍，表述边界严格限制在当前仓库已经实现的能力内。

## 一句话版本

基于 FastAPI、LangGraph、DuckDB 和 SQLite 搭建结构化表格数据分析 Agent MVP，打通“CSV / Excel 上传 - 字段画像 - 业务语义检索 - 分析计划 - 工具执行 - 图表与报告生成 - 规则评估 - 事件追踪”的真实后端闭环。

## 简历项目描述版本

- 基于 FastAPI 设计并实现结构化表格分析后端，支持 CSV / Excel 上传、字段画像生成、任务创建与分析结果查询。
- 以 LangGraph 编排最小分析状态流，串联字段匹配、DuckDB 聚合、显式 `route_next_step` 路由、图表配置生成、结构化报告生成和规则评估流程，并对多指标问题继续执行下一轮工具统计。
- 在字段识别阶段生成显式 `planned_tool_calls`，把受控工具执行计划写入状态，再由后续节点逐步消费，增强 Tool Use 过程的可追踪性。
- 使用 Pydantic 约束报告输出 Schema，确保 `generate_report` 产出的结构化报告在返回前经过显式校验。
- 设计可替换 `LLMClient` 接口，使用 `MockLLM` 驱动分析目标和计划生成，确保 MVP 在无外部模型依赖下仍可真实运行。
- 构建本地 JSONL 关键词检索模块，为字段语义理解和分析计划提供轻量业务上下文增强。
- 设计 Redis 优先、SQLite 降级的会话状态存储方案，并将报告草稿、中间发现和业务上下文拆分为细粒度 key 保存，提升任务恢复和过程追溯能力。
- 使用 SQLite 持久化文件元数据、任务状态、事件时间线、工具调用日志和评估结果，并新增固定 case 回归评测能力验证主链稳定性。

## 面试中可展开的工程点

- 为什么在 MVP 阶段先做 MockLLM + 轻量 RAG，而不是直接接真实模型
- 为什么 CSV 明细计算必须交给 DuckDB/工具链，而不是交给大模型
- 为什么要把事件时间线和规则评估一起纳入主链，而不是最后再补日志
- 为什么用固定 case 回归去验证“真实支持边界”，避免 README 和简历漂移
